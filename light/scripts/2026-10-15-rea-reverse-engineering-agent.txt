# What is REA?
REA stands for reverse engineer anything. It's an open-source MCP server. MCP, the model context protocol, is the standard way AI agents call external tools. REA plugs into agents like Claude Code, Codex, and Cursor and hands them a reverse engineering toolkit. It doesn't decompile anything by itself. The heavy lifting is done by established tools like Ghidra, IDA, and Hopper. REA drives them and everything runs locally on your machine. Getting started takes a single setup command shown on screen.
# How reverse engineering works (disassembly, decompilation)
When software ships, a compiler has already turned its source code into machine instructions, raw bytes the processor executes, names, comments, structure, mostly gone. Reverse engineering means going backwards. Step one is disassembly. Each group of bytes becomes one instruction. Push, move, multiply, return. That's assembly. It's exact but very low level. Step two is decompilation. A decompiler rebuilds C like pseudo code with functions, variables, and loops. But that's a reconstruction. Sometimes it drops inputs, merges steps, or loses the math entirely. And decompiled code isn't source code. It doesn't come with the original names or any right to use it.
# Why a language model can help
So why can a language model help? Because assembly is a language with a small vocabulary and patterns that repeat across millions of programs. Models trained on huge amounts of code are good at spotting them. But a model can also invent things that look right. In reverse engineering, a confident guess is worse than no answer. That's the problem REA is designed around.
# REA's architecture
Here's the architecture. Your agent calls REA through MCP. The same workflows also run from the command line. Inside REA, an application layer runs the investigation and keeps a session for each target. A provider registry picks one analysis engine per target deterministically with no silent fallback. Below that are the providers. Ghidra, IDA, and Hopper for native binaries, JADX for Android, a browser for websites, plus readers for .NET, web assembly, and firmware. Each one runs in its own managed process with deadlines and cleanup, and every result comes back up as structured evidence.
# Structured evidence: unknown is not absent
Every result carries an ID, the exact location it came from, and how much of the target was covered. If REA didn't observe something, it reports it as unknown, not as absent. So, the agent can't quietly turn a gap into a fact. And because a binary can hide text written to trick an AI, like run this command, REA marks target content as untrusted, the agent treats it as data, never as instructions.
# Case study: DX-Ball's stereo pan, 63 bytes
Now, back to those 63 bytes. The game is DX Ball, a brick breaker from the 1990s. When the ball hits a brick, the sound leans left or right depending on where the brick is. How is that calculated? Ghidra's decompiler returned a function with no inputs and none of the math. So the agent read the assembly through REA: one integer argument, then multiply, subtract, multiply. Two of those instructions read constants from memory. The agent asked REA for the raw bytes, decoded them: 1.5625 and 500. Then it followed the caller. The brick's position times 30 plus 20. That's its horizontal position on screen.
# The rebuilt formula
So pan equals x times 1.5625 minus 500, times a scale. Check the middle of a 640 pixel screen. 320 times 1.5625 is 500, minus 500 is 0. Dead center. # Beyond native binaries
REA goes far beyond native binaries. Electron apps, Android apps, web assembly, firmware, websites, network captures, even smart contract byte code.
# Rebuild behavior, don't copy code
But it's not a clone button. Rebuilding behavior is one thing. Copying someone's code is another. REA is built for security, research, education, interoperability, preservation, and software you're authorized to examine. It won't help bypass DRM, build cheats, or copy proprietary code.
